先讀這裡：這套 Skills 怎麼用

mattpocock/skills 不是一個自動接管整個專案的框架，而是一套可組合的工程工作法。你可以只在需要時使用其中一項技能，也可以把多項技能串成完整流程。

規劃

先對齊再動工

grill-with-docs、domain-modeling、to-spec 把口語需求轉成領域語言、ADR 與可驗證規格。

實作

小步、垂直切片

to-tickets、implement、tdd 將工作切成可在單一上下文完成的 tracer bullet。

驗證

需求與品質分開審

diagnosing-bugs、code-review、improve-codebase-architecture 建立回饋迴路並檢查規格符合度與程式異味。

不同 Agent 的呼叫語法不相同 專案 README 經常以 /skill-name 表示技能，但實際使用時：Codex 建議輸入 $skill-name；OpenCode 通常在提示詞中指名技能，由原生 skill tool 載入；Antigravity CLI 會把 Skills 轉成 slash commands，可直接輸入 /skill-name。Antigravity IDE 則可在提示詞中指名技能。
最適合你的預設策略 將 Skills 安裝在每個專案的 .agents/skills/，並提交到 Git。這能同時被 Codex、OpenCode 與 Antigravity 辨識，也不會影響其他專案或全域設定。

開發新專案流程及每一步驟的使用方式

1
專案初始化Git、測試、型別與 CI 基線
2
SetupIssue Tracker 與文件布局
3
Grill + Domain釐清需求與共同語言
4
Spec正式規格與測試 seam
5
Tickets垂直切片與依賴
6
Implement + TDD逐張實作
7
Code Review標準與規格雙軸審查
1

建立最小可驗證專案基線

先讓 Agent 能快速取得「成功／失敗」訊號。至少建立建置、型別檢查、單元測試與格式化命令。新專案不要先塞入大量抽象層。

  • 初始化 Git，建立第一個乾淨 commit。
  • 確認一條最小測試命令可執行。
  • 在 AGENTS.md 記錄建置、測試與禁止事項。
  • 敏感資料放入環境變數，不放入 prompt、skill 或 repo。
先分析此空白專案的目標與技術限制。只建立最小可執行骨架、測試命令與 AGENTS.md 基線，不要實作業務功能，也不要自行 commit。
2

執行 setup-matt-pocock-skills

此步驟只需每個 repo 執行一次。它會檢查 Git remote、現有 AGENTS.md/CLAUDE.md、CONTEXT.md、ADR 與 monorepo 訊號，再設定 Issue Tracker 和領域文件位置。

建議選項

  • Issue Tracker：有 GitHub remote 就選 GitHub。
  • 單人或實驗專案：可選 local markdown。
  • Domain docs：一般 repo 選 single-context。
  • 沿用既有 AGENTS.md，避免重複建立 CLAUDE.md。

針對你的目錄習慣

在 setup 期間明確要求規劃與修補文件繼續放在既有 plan/、plan/troubleshooting/、plan/break_plan/，不要重複建立相同用途的資料夾。

使用 setup-matt-pocock-skills 設定此 repository。沿用現有 AGENTS.md；Issue Tracker 使用 GitHub；領域術語使用根目錄 CONTEXT.md；ADR 使用 docs/adr；既有開發計畫仍存放於 plan/，不要建立重複用途的 specs 目錄。先顯示草稿，未經我核准不得寫檔。
3

使用 grill-with-docs 釐清產品與領域

讓 Agent 一次詢問一個真正會改變設計的問題。回答時提供具體案例、角色、狀態轉換、例外與資料來源。過程中以 domain-modeling 更新共同語言。

  • CONTEXT.md 只放「名詞及其精確含義」，不要放檔案路徑與類別名稱。
  • 只有難以逆轉、未來讀者會疑惑、且有真實取捨的決策才建立 ADR。
  • 遇到 UI 或行為難以文字決定時，先用 prototype 做可拋棄原型。
使用 grill-with-docs 釐清此專案。請從使用者角色、核心業務流程、狀態轉換、錯誤處理、權限和資料生命週期開始；一次只問一個問題。同步維護 CONTEXT.md，ADR 必須符合難以逆轉、令人意外、存在真實取捨三個條件。
4

使用 to-spec 將討論固化成規格

to-spec 不再訪談，而是把現有對話與 codebase 理解整理成規格。它會要求先確認測試 seam，並建立 Problem、Solution、User Stories、Implementation Decisions、Testing Decisions、Out of Scope。

不要太早使用若重要需求仍不清楚，先回到 grill-with-docs；否則規格只會把模糊內容正式化。
使用 to-spec 把目前已確認的需求整理成規格。先提出建議測試 seam，等我核准後再發布。規格禁止寫入容易過期的檔案路徑與程式片段；明確列出 Out of Scope。
5

使用 to-tickets 拆成 tracer-bullet tickets

每張 ticket 應完成一條窄但完整的路徑，例如資料、API、UI 與測試，而不是「先把所有資料庫改完」。每張 ticket 必須能獨立展示或驗證，並適合一個新的上下文視窗完成。

  • 先完成必要 prefactor，再做功能切片。
  • 每張 ticket 標明 Blocked by。
  • 廣泛 rename 或 schema 變更使用 expand → migrate batches → contract。
  • 發布前先讓你確認顆粒度、依賴是否正確。
使用 to-tickets 將此規格拆成垂直切片。每張 ticket 必須在一個全新上下文中可完成、可獨立驗證，並標出 blocking edges。先顯示草稿，不要建立 GitHub Issues，等我核准後再發布。
6

逐張使用 implement，並在約定 seam 套用 tdd

一次只處理一張 frontier ticket。先讀 spec、CONTEXT.md 與相關 ADR；確認測試 seam；執行一個測試、一個最小實作的垂直循環。定期跑 typecheck 與單一測試，最後才跑完整套件。

原始 implement skill 會自動 commit這和你常用的「先審查、再決定是否提交」不一致。建議修改專案內的本機 skill，要求完成後只輸出變更與驗證摘要，除非使用者明確要求，否則不得 commit、push 或建立 PR。
使用 implement 實作 ticket「建立訂單最小成功路徑」。使用 tdd，先提出並確認測試 seam；只處理本 ticket，不擴大範圍。完成後執行 code-review，但不要 commit、push 或建立 PR。
7

使用 code-review 雙軸審查

指定固定比較點，例如 main、某 commit 或 merge-base。Standards 軸檢查專案規範與 Fowler smells；Spec 軸檢查漏做、做錯與 scope creep。兩軸報告保持分開，不要互相抵銷。

使用 code-review 審查從 main 到目前 HEAD 的變更。Spec 來源是 GitHub Issue #123；Standards 來源包含 AGENTS.md、CONTRIBUTING.md 與既有慣例。只回報可操作問題，不要修改程式。

完成條件：spec 驗收條件全部有證據、測試通過、沒有未要求功能、沒有未處理高風險審查項目，才進入人工核准與 commit。

重大修改或重構流程及每一步驟的使用方式

1
建立基線現況、測試、效能、相容性
2
Architecture Scan找出高價值候選
3
Wayfinder處理未知與決策
4
Spec + Tickets展開／遷移／收縮
5
Incremental Change每批保持可回復
6
Review + Compare行為、效能、相容性
1

凍結現況與成功標準

重大修改前先建立可比較基線：現有測試結果、代表性輸入輸出、SQL 快照、效能指標、資料庫版本、API 相容範圍與回滾方式。

  • 保存代表性 fixtures 與 golden outputs。
  • 記錄目前失敗測試，不把既有問題誤認為重構造成。
  • 列出不可破壞的 public contracts。
  • 建立回滾點與資料 migration 回復方案。
2

使用 improve-codebase-architecture 掃描摩擦

先限定範圍，優先檢查近期常被修改的 hot spots。該 skill 會用 module、interface、depth、seam、adapter、leverage、locality 等共同詞彙，產生含 before/after 視覺的 HTML 報告。

使用 improve-codebase-architecture 分析 SQL 產生器與 dialect 模組。先讀 CONTEXT.md、相關 ADR 與最近 100 次 commit；找出造成測試困難、跨檔案跳轉與 dialect 洩漏的深層原因。只產生候選報告，不要修改程式。
3

選定候選後以 grilling 決定新 seam

不要一次接受所有建議。先選一個最有 leverage 的候選，釐清哪些行為應藏在深模組後方、哪些介面必須保持穩定，以及哪些測試能跨重構存活。

若仍有大量未知、跨多個 session 才能決定，啟動 wayfinder，將研究、原型、訪談與任務分成決策 tickets。

4

建立重構規格與 expand–contract tickets

重大重構要明確分離「行為不變」與「新增能力」。對廣泛 API、欄位、型別或 SQL AST 變更，使用：

階段做法通過條件
Expand加入新介面／欄位／AST 節點，舊形式仍可運作舊測試全部通過，新路徑有測試
Migrate依套件或功能批次遷移呼叫者每一批可獨立合併且保持綠燈
Contract確認無舊呼叫者後移除舊形式搜尋、測試與文件均無殘留
使用 to-spec 產生「SQL AST 與 dialect 分離」重構規格，保證外部查詢結果與參數綁定契約不變。再用 to-tickets 建立 expand、分批 migrate、contract tickets，標明依賴與回滾方式。
5

逐批實作，避免 Big Bang

  • 一次只做一個結構變更或一個 caller batch。
  • 先建立 characterization tests，鎖住既有行為。
  • 對 SQL 使用同一組輸入同時跑舊版與新版，做 differential comparison。
  • 資料 migration 使用雙寫、影子讀取或可回退策略。
  • 禁止順便做無關格式化，避免 diff 難審。
6

以固定點執行 code review 與前後比較

除了單元測試，重大重構還要比較：

  • 公開 API／SQL／資料格式是否完全相容。
  • 效能是否退化。
  • 錯誤訊息、transaction 邊界與 NULL 行為是否改變。
  • 新模組是否真的降低 interface 複雜度，而非只搬檔案。
使用 code-review 審查 base commit abc1234 到 HEAD。Spec 軸確認所有外部 SQL、參數順序與錯誤契約維持不變；Standards 軸聚焦 module depth、dependency direction、duplication 與 speculative generality。不要自行修正。

Bug 修正流程及每一步驟的使用方式

1
Feedback Loop一條會抓到該 Bug 的命令
2
Reproduce重現並最小化
3
Hypotheses3–5 個可否證假設
4
Instrument一次改一個變因
5
Regression Test先紅、修正、再綠
6
Cleanup原始情境與審查
最重要原則沒有一條能針對使用者所描述症狀「變紅」的快速命令，就不要先猜根因。diagnosing-bugs 把建立回饋迴路視為整個除錯工作的核心。
1

建立緊密回饋迴路

依序嘗試 failing test、curl、CLI fixture、headless browser、trace replay、throwaway harness、property/fuzz、git bisect 或 differential loop。目標是一條已實際跑過、可自動執行、速度以秒計、能抓到精確症狀的命令。

使用 diagnosing-bugs 處理「同一張訂單偶爾重複扣庫存」。第一階段只建立能抓到此精確症狀的 deterministic feedback loop；在有 red-capable command 前，不要提出根因或修改程式。
2

重現並縮小到最小案例

逐一刪除輸入、設定、呼叫者與資料，刪除後仍重現才繼續。最終每一個剩餘元素都必須是 load-bearing。

3

列出 3–5 個可否證假設

每個假設都要有預測：「如果 X 是原因，改變 Y 就會讓 Bug 消失／惡化」。先呈現排序，讓領域專家快速重新排序，但不必因無人回覆而停止。

4

精準 instrumentation

優先 debugger／REPL，其次在能區分假設的邊界加入帶唯一前綴的 targeted logs。效能問題先建立 baseline、profile 或 query plan，不要以大量 log 代替量測。

5

在正確 seam 建立回歸測試，再做最小修正

  1. 把最小重現轉成 failing test。
  2. 確認測試確實先失敗。
  3. 套用最小修正，不順便重構。
  4. 確認測試通過。
  5. 重新跑原始未縮小情境。

若沒有能重現真實 Bug 模式的 seam，需明確記錄「架構阻止建立可靠回歸測試」，修正完成後再交給 improve-codebase-architecture。

6

清理與 code review

  • 移除所有 [DEBUG-...] instrumentation。
  • 刪除 throwaway harness，或移到明確 debug 位置。
  • 在修正說明記錄真正根因，而不只寫「fix bug」。
  • 使用 code-review 比較修正前 fixed point，確認沒有 scope creep。
使用 code-review 審查 Bug 修正 commit。Spec 軸以原始 Bug 報告及重現案例為準；Standards 軸確認沒有加入廣泛重構、無關格式化或只為測試而暴露私有實作。

大型專案流程及每一步驟的使用方式

當目標大到一個 agent session 放不下，而且尚有大量決策未知時，不要先建立數十張實作 ticket。先使用 wayfinder 建立決策地圖。

1
Name Destination清楚定義抵達條件
2
Chart Map決策、fog、out of scope
3
Research / Prototype並行清除外部未知
4
Resolve Frontier每 session 一張決策票
5
Spec + Tickets方向清楚後才切實作
6
Incremental Delivery逐張實作與審查
1

命名 Destination

Destination 不是模糊的「完成 ERP 改造」，而是可判定的終點，例如「完成經核准、可交給實作團隊的 SQL 產生機制 v2 規格與遷移路線」。它會決定 scope。

2

建立 Map issue

Map 是低解析度索引，不重複儲存所有細節。內容包含 Destination、Notes、Decisions so far、Not yet specified、Out of scope。可精確描述的問題建立 child decision tickets，尚不能精確提問的內容保留在 fog。

使用 wayfinder 為「將既有 SQL 字串拼接改為可驗證 AST 與多 dialect 架構」建立決策地圖。Destination 是完成經核准的規格、遷移策略、相容性矩陣與驗證計畫；目前只規劃決策，不實作程式。
3

選擇 ticket 類型

類型適用情境例子
Research需要外部文件或既有系統事實確認三種資料庫的 pagination、NULL ordering 與參數限制
Prototype需要具體可運行產物才能決定比較兩種 AST interface 與錯誤模型
Grilling需要人類領域決策是否允許 caller 提供 raw SQL escape hatch
Task需要先完成一件事才能做決策匯出現有 production SQL 樣本並去識別化
4

每個 session 只解一張 frontier ticket

先 claim，再讀必要的相關決策；完成後將答案記錄為 resolution、關閉 ticket、在 Map 中新增一行 context pointer，並依新資訊新增或調整 tickets。不要每次載入整張地圖所有細節。

5

路線清楚後，才轉成規格與實作 tickets

當所有抵達 Destination 前的決策都已清楚，使用 to-spec 固化；再用 to-tickets 建立可執行的垂直切片。Wayfinder tickets 是「決策」，to-tickets 產物才是「要建造的工作」。

6

控制上下文與多 Agent 併行

  • 每張 ticket 使用新 session，先讀 Map gist、該 ticket、相關 CONTEXT/ADR。
  • 只併行無 blocking edge 的 frontier tickets。
  • 共享成果透過 Issue、commit、ADR、CONTEXT.md，不靠聊天記憶。
  • 實作階段可再搭配 Git worktree 或 SwarmForge，但 Skills 保持工程方法來源。

Codex 安裝方式詳細步驟

推薦範圍：專案級Codex 官方會從目前目錄一路掃描到 repo root 的 .agents/skills/。專案級安裝可提交到 Git，團隊與其他 Agent 也能共用。

步驟 1：安裝必要工具

準備 Git、Node.js LTS（提供 npm/npx）以及 Codex。若尚未安裝 Codex CLI：

npm install -g @openai/codex
codex --version

步驟 2：進入專案根目錄並列出可安裝 Skills

cd path/to/your-project
npx skills@latest add mattpocock/skills --list

步驟 3：互動式安裝到 Codex

npx skills@latest add mattpocock/skills -a codex

安裝時建議：

  • Scope 選 Project。
  • 至少選 setup-matt-pocock-skills。
  • 再選本指南核心技能：grill-with-docs、grilling、domain-modeling、to-spec、to-tickets、implement、tdd、diagnosing-bugs、code-review、codebase-design、improve-codebase-architecture、wayfinder、research、prototype。
  • Windows 若 symlink 失敗，重跑並選 Copy，或加 --copy。

# 專案目錄應可看到：

OpenCode 安裝方式詳細步驟

步驟 1：安裝 OpenCode

Windows 11 可直接安裝，但官方建議 WSL 以取得較完整的終端與檔案系統相容性。

WSL / Linux / macOS

curl -fsSL https://opencode.ai/install | bash
opencode --version

Windows 原生 npm

npm install -g opencode-ai
opencode --version

第一次啟動後使用 /connect 設定模型供應商。OpenCode 本身通常需要你選擇並授權 LLM provider。

步驟 2：在專案根目錄安裝 Skills

cd path/to/your-project
npx skills@latest add mattpocock/skills -a opencode

建議 Project scope。skills CLI 會安裝到 OpenCode 可辨識的專案技能位置；目前 OpenCode 會掃描 .opencode/skills、.claude/skills 與 .agents/skills。

步驟 3：驗證 Skills

npx skills list -a opencode
opencode

OpenCode 不保證把每個 Skill 直接變成 slash command。最穩定做法是在提示詞中明確寫：

Use the setup-matt-pocock-skills skill to configure this repository. Show the proposed files before writing.

Agent 會透過原生 skill tool 載入。若沒有載入，可要求：「先列出 available skills，然後載入 setup-matt-pocock-skills」。

步驟 4：確認權限

若 Skills 不可見，檢查 opencode.json 是否禁止 skill tool。可以設定：

{
  "$schema": "https://opencode.ai/config.json",
  "permission": {
    "skill": {
      "*": "allow"
    },
    "bash": "ask",
    "edit": "ask"
  }
}
相容性注意OpenCode 只辨識標準 frontmatter 欄位，未知欄位會被忽略。因此 Matt Skills 中的 disable-model-invocation: true 不會在 OpenCode 中強制「只能手動呼叫」。若你不希望某些技能被自動選用，可透過 OpenCode skill permissions 限制，或調整專案內 skill 的 description。

步驟 5：Windows 建議路徑

大型 repo 建議放在 WSL 自己的檔案系統，例如 ~/code/project，而不是長期放在 /mnt/c 或 /mnt/d。若必須存取 Windows 目錄仍可使用，但 Git、watcher 與大量小檔案作業通常在 Linux filesystem 較順。

agy --version

CLI 會嘗試使用作業系統安全 keyring；沒有既有 session 時會開啟瀏覽器進行 Google Sign-In。SSH 環境會提供授權 URL 與代碼流程。

其他重要建議及實際操作範例

範例一：新 ERP 模組

目標 建立採購請款模組，包含申請、審核、退回、付款與稽核。

  1. Setup：確認 GitHub Issues、CONTEXT.md、ADR 與 plan/ 路徑。
  2. Grill：釐清 Request、Approval、Payment、Rejection 等領域詞彙與狀態。
  3. Prototype：先做狀態機或操作畫面原型，讓財務人員確認。
  4. Spec：固化角色、user stories、權限、錯誤與測試 seam。
  5. Tickets：建立「提交最小請款」、「主管核准」、「退回補件」、「付款完成」等垂直切片。
  6. Implement：一張一張以 TDD 完成。
  7. Review：對照 spec 與 coding standards。
使用 grill-with-docs 規劃採購請款模組。先建立領域語言，尤其區分請款單、付款單、核准、退回與作廢；用具體情境檢查部分核准、重複付款、跨期與權限代理。未完成需求釐清前不要建立程式碼。

範例二：SQL 產生器重大重構

  1. 用 improve-codebase-architecture 找出 dialect 洩漏與 shallow modules。
  2. 用 wayfinder 分別決定 AST、binding、quoting、pagination、NULL、transaction 與 migration。
  3. 建立舊版/新版 differential harness。
  4. 用 expand–contract tickets 逐步遷移。
  5. 每一批執行 SQL snapshot、實際 DB integration tests 與 code review。
使用 wayfinder 規劃 SQL 產生器 v2。Destination 必須包含：核准的 AST public interface、MySQL/PostgreSQL/SQL Server dialect 矩陣、參數綁定規則、舊 API 遷移方式、差異測試與回滾策略。只建立決策地圖，不直接寫程式。

範例三：偶發 Session 錯亂

  1. diagnosing-bugs 建立可大量重跑的多 session harness。
  2. 提高重現率，固定亂數、時間與測試資料。
  3. 列出 session key collision、共享 cookie jar、race condition、cleanup 過早等可否證假設。
  4. 在正確 boundary 加 instrumentation。
  5. 先建立 regression test，再修正。
  6. 若無法在 public seam 測試，修正後另外建立 architecture ticket。
使用 diagnosing-bugs 分析多使用者 Session 偶爾互相污染。先建立可以平行模擬至少 50 個使用者並驗證 session 隔離的 feedback loop；沒有重現命令前禁止猜測根因。

範例四：只審核計畫，不寫程式

讀取指定計畫、CONTEXT.md、ADR 與目前 codebase。使用 code-review 的 Spec/Standards 分離思維審核計畫，但不要執行 implement、不要修改任何檔案、不要 commit。輸出阻斷問題、風險、缺少驗證及建議的 ticket 切分。

範例五：跨上下文交接

使用 wayfinder 管理此長期工作。每次 session 僅處理一張 frontier ticket；完成後把決策、證據、影響與下一步寫回 Issue/Map。不要依賴聊天摘要作為唯一交接來源。

其他重要建議

1. 優先專案級，不要一開始全域安裝

專案不同，術語、測試、Issue Tracker 與安全限制也不同。將 skills 放在 .agents/skills/，讓行為可被 review、版本控制與回退。

2. 安裝前先讀 Skill

Skill 是會影響 Agent 決策的操作性文字，有時還帶 scripts。第三方 skill 應視為程式碼供應鏈的一部分，先檢查指令、外部下載、刪除與自動提交行為。

3. 修改 implement 的提交規則

建議將「Commit your work」改成「除非使用者明確要求，不得 commit、push、merge 或建立 PR」。這符合你先審核結果的工作方式。

4. 控制 Skill 數量

安裝太多會增加初始技能清單與選擇混亂。依專案只保留實際需要的核心組合，實驗性或個人技能不要直接導入正式 repo。

5. 規格與術語分開

CONTEXT.md 是 glossary，不是需求書；spec 是本次改動要求；ADR 是難以逆轉的架構取捨；AGENTS.md 是長期操作規則。不要混成一份巨型文件。

6. 用證據結束任務

完成報告至少應列出變更、測試命令與結果、未解風險、spec 對應與未執行項目。不要只說「已完成」。

建議加入專案 AGENTS.md 的規則

## Agent skills operating rules

- Skills are project-scoped under `.agents/skills/`; do not change global skills.
- Existing planning documents remain under `plan/`; do not create duplicate-purpose folders.
- Before implementation, read `CONTEXT.md`, relevant ADRs, and the originating spec/ticket.
- Do not commit, push, merge, create a PR, or modify issue state unless explicitly requested.
- For large work, use one fresh session per frontier ticket and persist decisions in the tracker.
- For bugs, establish a red-capable reproduction command before proposing a root cause.
- Report exact verification commands and results at handoff.

建議工作流選擇表

工作最小技能組合不要先做
新功能grill-with-docs → to-spec → to-tickets → implement → code-review直接讓 Agent 自由實作整個需求
小型 Bugdiagnosing-bugs → tdd → code-review先猜原因、先大幅重構
重大重構improve-codebase-architecture → grill/wayfinder → to-spec → to-tickets → review一次取代所有舊介面
長期大型專案wayfinder → research/prototype/grilling → to-spec → tickets在未知仍很多時先切幾十張實作票
純計畫審核domain-modeling + code-review 思維啟動 implement 或自動 commit

故障排除

安裝後看不到 Skills
  1. 確認檔名是大寫 SKILL.md。
  2. 確認 YAML frontmatter 有 name 與 description。
  3. 確認資料夾位於 repo root 的 .agents/skills/<name>/。
  4. 重新啟動 Agent 或開新 session。
  5. 用 npx skills list 檢查安裝結果。
Windows 建立 symlink 失敗

重新安裝並選 Copy，或加 --copy。Project skills 很適合直接複製並提交到 Git，代價只是更新時需重新同步。

Codex 無法用 /skill-name

Codex 的明確技能呼叫使用 $skill-name，或先輸入 /skills 選擇；/skill-name 不是通用格式。

OpenCode 沒有對應 slash command

這是正常現象。用自然語言寫「Use the xxx skill」，OpenCode 會透過原生 skill tool 載入。再檢查 opencode.json 的 skill permission。

Antigravity CLI 找不到 skill

確認 workspace 路徑是 .agents/skills/，不是舊的 .gemini/skills/。在 CLI 執行 /skills，必要時結束後重新從 repo root 執行 agy。

setup 想建立不需要的文件結構

先要求它顯示草稿；明確指定沿用 AGENTS.md 與現有 plan/，並將你的偏好寫入 setup 產生的 docs/agents/*.md。不要在未審核時直接接受寫入。

Agent 自動使用了原本想手動啟動的 skill

Codex 可在 agents/openai.yaml 設定 policy.allow_implicit_invocation: false。OpenCode 可用 skill permissions；Antigravity 可調整 description 或只在需要的 repo 安裝。
